# 投稿与 Rebuttal：从提交检查到证据回应

投稿和 rebuttal 不是排版收尾，而是对研究主张进行最后一次压力测试。

## 投稿前冻结什么

至少冻结：

- 数据版本；
- 代码 commit；
- 配置文件；
- 主实验结果；
- 图表生成脚本；
- 参考文献库；
- supplementary 内容。

如果投稿后仍频繁改动核心实验，说明研究尚未稳定。

## 投稿检查

### 研究主张

- 每个贡献是否具体；
- 是否把工程实现包装成机制创新；
- 是否声明超出实验覆盖范围；
- limitation 是否真实；
- 负结果是否影响核心结论。

### 实验

- baseline 是否完整且公平；
- 超参数预算是否一致；
- 随机种子和误差是否报告；
- 消融是否对应方法主张；
- 指标是否真正测量目标能力；
- 表格和正文数字是否一致。

### 写作与格式

- 模板、页数、匿名和补充材料符合要求；
- PDF 中无作者、单位或仓库泄漏；
- 图片缩放后可读；
- 引用真实且支持陈述；
- 所有交叉引用可解析。

## 内部审稿

至少安排三种视角：

1. 领域审稿人：检查 novelty 和 closest work。
2. 方法审稿人：检查实验、统计和替代解释。
3. 非项目成员：检查论文是否能被独立理解。

内部审稿问题：

```text
论文最核心的一个主张是什么？
最可能被拒绝的原因是什么？
哪个实验缺失会使结论无法成立？
是否存在更简单的解释？
哪一段最像作者自我说服？
```

## Rebuttal 分类

收到评论后先分类，不要立即逐句反驳：

- 事实误解；
- 写作不清；
- 缺少实验；
- baseline 不充分；
- novelty 质疑；
- 评价指标质疑；
- 结论过强；
- 审稿意见本身相互冲突。

## 回应优先级

1. 影响接收判断的核心问题。
2. 多位审稿人共同提出的问题。
3. 可以用现有证据澄清的问题。
4. 能在时间内完成且有判别力的新实验。
5. 纯格式和次要表达问题。

不要为了显得勤奋而补大量无关实验。

## 一个合格回应的结构

```text
感谢并复述问题
→ 明确当前论文中哪里不清楚
→ 给出已有或新增证据
→ 说明证据支持的范围
→ 写明将如何修改论文
```

示例：

```text
审稿人质疑提升是否来自更大的参数量。
我们补充参数匹配 baseline，并保持训练预算一致。
在三个随机种子下，方法仍提升 X±Y。
这支持收益并非仅由参数量增加导致，但不能证明所有模块都必要。
我们将在表 3 和方法限制中补充说明。
```

## 新实验是否值得做

只在以下条件下补实验：

- 能直接回答核心质疑；
- 设置公平；
- 时间允许完成多次运行和检查；
- 无论正负结果都能解释；
- 不会引入新的未经验证主张。

一次仓促的单随机种子结果可能比不补实验更糟。

## 禁止做法

- 编造或选择性报告结果；
- 说“审稿人没有理解”但不承认写作问题；
- 用更多文字回避缺失证据；
- 将新结果描述得比实际更确定；
- 承诺无法在 camera-ready 完成的工作；
- 让 AI 自动生成事实回应而不核验。

## Camera-ready

接收后仍需：

- 合并 rebuttal 中承诺的修改；
- 恢复作者信息；
- 更新引用和致谢；
- 重新检查所有数字；
- 清理匿名占位符；
- 固定最终代码和材料版本；
- 保存提交 PDF、源文件和回执。

## 检查清单

- [ ] 回应覆盖核心质疑
- [ ] 每个事实有证据
- [ ] 新实验设置公平且可复查
- [ ] 没有扩大结论
- [ ] 修改位置明确
- [ ] 所有承诺可兑现
- [ ] 最终稿与 rebuttal 一致
