# 实验工具选择：从本地日志到 W&B、MLflow 与 DVC

实验工具的价值是降低遗漏和复现成本，不是增加仪表盘数量。

## 先判断是否需要升级

使用 Markdown、CSV 和 Git 已经能回答下面问题时，不必立刻引入复杂平台：

- 这次实验改了什么？
- 使用了哪个代码版本？
- 数据和配置是什么？
- 结果是否可重复？
- 与上一次实验相比有什么变化？

出现以下情况再升级：

- 并行实验很多；
- 多人共享实验；
- 参数维度复杂；
- 需要自动比较曲线和指标；
- 模型、数据和产物需要统一追踪；
- 手工日志已频繁漏记。

## 工具边界

| 工具 | 主要用途 | 不解决什么 |
| --- | --- | --- |
| Git | 代码和文本版本 | 大数据、模型权重和实验指标管理 |
| Hydra / 配置文件 | 参数组合和配置复用 | 实验结果展示和数据版本 |
| W&B | 实验指标、曲线、产物和团队协作 | 自动保证实验设计正确 |
| MLflow | 运行、参数、指标、模型和部署流程 | 自动发现数据泄漏或错误指标 |
| DVC | 数据和大文件版本 | 科研假设和结果解释 |
| Docker | 环境封装 | 硬件差异、外部服务和随机性完全一致 |
| Make / shell 脚本 | 固化运行命令 | 自动判断运行结果是否可信 |

## 最小升级路线

### Level 1：文件日志

```text
runs/<run_id>/
├── config.yaml
├── metrics.json
├── stdout.log
├── notes.md
└── figures/
```

### Level 2：统一配置

- 配置文件进入 Git；
- 命令行只覆盖少量字段；
- 每次运行自动保存最终配置；
- 运行目录记录 commit hash。

### Level 3：实验追踪平台

适合多个实验并行、多人协作或需要系统比较时。

应记录：

- 参数；
- 指标；
- 随机种子；
- 数据版本；
- 代码版本；
- 运行状态；
- 模型和输出产物；
- 失败原因。

### Level 4：数据和模型资产

当数据或权重无法直接进入 Git 时，再使用 DVC、对象存储或模型注册表。

## 工具不能替代的检查

即使平台记录完整，也必须人工确认：

- baseline 是否公平；
- 指标实现是否正确；
- 数据是否泄漏；
- checkpoint 是否选在公平节点；
- 多次运行是否独立；
- 失败运行是否被选择性删除；
- 图表是否只展示有利区间。

## 推荐运行元数据

```yaml
run_id: 20260720_rag_conflict_baseline_s42
objective: verify frequency bias under conflicting evidence
code_commit: abc1234
data_version: conflict-v2
model: model-name
seed: 42
config: configs/baseline.yaml
status: completed
primary_metric: conflict_accuracy
notes: baseline reproduction
```

## 失败实验也要记录

失败状态至少区分：

- 代码错误；
- 资源不足；
- 配置错误；
- 指标异常；
- 结果不支持假设；
- 被主动停止。

“没有提升”不是运行失败，而可能是重要研究证据。

## 迁移原则

从本地日志迁移到平台时：

1. 先统一字段和目录。
2. 再写自动记录代码。
3. 选择 3 到 5 个历史实验回填测试。
4. 确认导出能力和供应商迁移成本。
5. 不要让核心结果只能从网页手工读取。

## 检查清单

- [ ] 每次运行有唯一 ID
- [ ] 保存最终配置而非默认配置
- [ ] 记录代码和数据版本
- [ ] 指标可从原始输出重新计算
- [ ] 失败运行保留原因
- [ ] 关键产物可导出
- [ ] 密钥不进入仓库和日志
- [ ] 工具故障时仍能恢复核心实验信息
