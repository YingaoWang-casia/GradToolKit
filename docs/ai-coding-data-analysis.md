# AI 辅助代码、实验与数据分析

AI 可以帮助定位错误、补测试、解释代码和提出分析候选，但“看起来合理”不等于代码正确，更不等于实验结论成立。

## 代码任务的基本规则

每次使用 AI 修改代码，都至少保留：

```text
原始问题
复现命令
输入样例
预期行为
实际行为
修改内容
测试结果
仍未覆盖的风险
```

没有运行结果时，不应声称“已经修复”。

## 调试工作流

### 1. 先构造最小复现

不要直接上传整个项目并要求“修复所有问题”。先缩小到：

- 最短触发命令；
- 最小输入；
- 完整错误栈；
- 相关依赖版本；
- 预期输出；
- 最近一次已知正常版本。

### 2. 要求提出多个假设

AI 应输出：

```text
候选原因
支持证据
反对证据
最小验证方法
若验证失败，下一条不同路线
```

避免连续微调同一种解释。

### 3. 先写测试，再改实现

至少考虑：

- 正常输入；
- 空输入；
- 极端长度；
- 错误类型；
- 随机性；
- 数值精度；
- CPU/GPU 或不同设备；
- 批量维度和 shape；
- 数据缺失和重复。

### 4. 运行并保存证据

保存：

- 测试命令；
- 通过和失败数量；
- 关键日志；
- 运行环境；
- 性能变化；
- commit hash。

## 实验代码审计

让 AI 检查时，重点不是代码风格，而是科研风险：

- train、validation、test 是否泄漏；
- 随机种子是否真正生效；
- evaluation mode 是否正确；
- 数据预处理是否训练测试一致；
- 指标实现是否与论文定义一致；
- checkpoint 是否加载正确；
- gradient accumulation、batch size 和学习率是否匹配；
- early stopping 是否使用测试集；
- 多次运行是否覆盖旧结果；
- 日志中的配置是否为实际生效配置。

## 数据分析工作流

### 第一步：先描述数据

提供：

```text
每一列的含义和类型
样本量
缺失值
重复值
数据采集过程
分组方式
随机化方式
目标变量
可能的依赖关系
```

不要只给 CSV 就让 AI 自行猜测含义。

### 第二步：提出分析问题

区分：

- 描述性问题：发生了什么；
- 比较性问题：组间是否不同；
- 关联问题：变量是否相关；
- 因果问题：某因素是否导致结果；
- 预测问题：能否预测未知样本。

不同问题不能混用同一套结论语言。

### 第三步：检查统计假设

AI 可以列出候选检验，但研究者必须检查：

- 样本是否独立；
- 分布假设是否合理；
- 方差是否齐性；
- 是否存在重复测量；
- 是否进行了多重比较；
- 样本量是否足够；
- effect size 与置信区间是否比单一 p 值更重要；
- 指标是否因数据不平衡而失真。

### 第四步：分析失败样本

不要只让 AI 总结均值。要求分组分析：

- 哪些样本稳定成功；
- 哪些样本稳定失败；
- 哪些样本对随机种子敏感；
- 哪些条件下方法退化；
- 是否存在数据质量问题；
- 错误是否可以形成 taxonomy。

## AI 生成图表代码时

必须检查：

- 横纵轴和单位；
- 分组和聚合方式；
- error bar 定义；
- 是否隐藏原始点；
- 是否错误截断坐标轴；
- 排序是否改变解释；
- 图中数字是否来自当前结果文件；
- 脚本是否能从原始数据重新生成图。

具体绘图工具和出版规范放在第四阶段。

## 常见失败

- 复制 AI 代码后只看是否报错，不验证逻辑。
- 模型修改了指标实现，却没有与标准实现对照。
- 用测试集反复选择参数。
- 数据分析中把相关性写成因果性。
- AI 选择了不适用的统计检验。
- 只展示均值，隐藏方差和失败样本。
- 修复一个错误后没有运行回归测试。
- 依赖版本改变后仍声称复现了原结果。

## 最小提示词

```text
请先不要直接修改代码。
根据错误栈、最小复现、环境和预期行为，列出互相不同的候选原因。
每个原因给出最小验证步骤。
确认原因后再提供最小补丁，并同时给出测试：正常输入、边界输入和回归测试。
不要在没有运行结果时声称已经修复。
```
