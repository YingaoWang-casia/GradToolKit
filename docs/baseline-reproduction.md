# 第一次复现 Baseline

复现的目标不是“把代码跑起来”，而是确认你理解了任务、数据、实现和评价口径，并获得后续实验可信的比较起点。

## 复现前先判断是否值得做

优先复现满足以下条件的工作：

- 是你课题的直接 baseline；
- 有公开代码或足够完整的实现细节；
- 数据和评价脚本可获得；
- 计算预算在可承受范围内；
- 复现结果能影响你是否继续当前方向。

不要从最复杂、最昂贵或依赖大量私有数据的方法开始。

## 复现成功的最低标准

复现不是必须与论文数字完全一致，但必须解释差异。最终报告至少包含：

```text
论文报告结果：
你的复现结果：
差异大小：
使用的代码版本：
数据版本：
模型或 checkpoint：
环境和硬件：
关键参数：
评价脚本：
已确认的差异来源：
仍未解释的差异：
```

## 第一步：冻结复现对象

先固定：

- 论文版本；
- 官方代码 commit；
- 数据集版本与划分；
- 模型 checkpoint；
- 论文中的目标表格或指标；
- 硬件与预算上限。

不要一边复现一边随意切换代码分支、数据预处理或指标实现。

## 第二步：先跑最小样例

顺序应是：

1. 单条样本完成前向流程；
2. 小数据子集完成训练或推理；
3. 检查输入、中间结果和输出；
4. 再运行完整实验。

直接跑完整训练会把实现错误变成数小时或数天的算力浪费。

## 第三步：核对五个高风险位置

### 数据

- 下载版本是否一致；
- train/dev/test 划分是否一致；
- 是否遗漏过滤规则；
- 是否发生数据泄漏；
- 文本清洗和截断是否一致。

### 模型

- checkpoint 是否正确；
- tokenizer 与模型是否匹配；
- 是否使用论文中的初始化方式；
- 参数量和可训练参数是否一致。

### 训练

- batch size 是否指单卡还是全局；
- 学习率是否随卡数调整；
- gradient accumulation 是否一致；
- seed、epoch、warmup 和 scheduler 是否一致。

### 推理

- beam size、temperature、top-p 是否一致；
- 最大长度和停止条件是否一致；
- 是否使用额外检索、后处理或 reranking。

### 评价

- 指标实现是否相同；
- macro 与 micro 是否混淆；
- 是否使用官方 evaluation script；
- 是否对缺失预测、重复样本做了相同处理。

## 第四步：建立差异诊断顺序

假设论文报告 82.4，你只能得到 77.1，不要立即调参。按以下顺序检查：

```text
评价脚本
→ 数据版本与预处理
→ checkpoint 与推理参数
→ 训练配置
→ 随机种子与方差
→ 硬件或库版本
→ 论文未公开细节
```

评价和数据问题通常比“模型没调好”更值得优先怀疑。

## 第五步：区分三种复现结论

### 已复现

结果处于论文报告区间或合理方差内，关键设置一致。

### 部分复现

趋势一致，但绝对数值存在可解释差异，例如硬件、数据版本或训练预算不同。

### 未复现

关键结果或趋势无法重现，且差异来源尚不明确。

不要为了显得顺利，把“未复现”写成“基本复现”。

## 什么时候联系作者

联系前应提供：

- 论文与代码版本；
- 完整运行命令；
- 环境信息；
- 最小复现日志；
- 你已经排除的原因；
- 一个具体问题。

不要只发“代码跑不出来，请问怎么办”。

## 复现报告模板

```text
# Baseline 复现报告

## 目标
要复现论文中的哪张表、哪一行、哪个指标？

## 环境
代码 commit、依赖、CUDA、GPU、数据版本。

## 配置
训练、推理、评价关键参数。

## 结果
论文结果、复现结果、多 seed 结果和方差。

## 差异分析
已确认原因、可能原因、已排除原因。

## 结论
能否作为后续实验 baseline？有哪些风险？
```

## 完成检查

复现完成后，你应能回答：

- 结果由哪段代码和哪份数据产生；
- 一条命令是否能重新生成主要结果；
- 论文数字与你数字为何不同；
- 这个 baseline 是否公平、稳定且适合后续比较；
- 哪些未公开细节仍可能影响结论。
